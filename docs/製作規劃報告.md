## 1. 製作方向

依本次需求，先完成「遊戲本體與確切流程」，再完成「營運後台、雙螢幕啟動與 touch service 實機整合」。第一階段就建立共用的遊戲狀態、輸入介面與場域配置，避免後台完成時重寫遊戲。

前期曾建議先做數字方格與數字速記，再逐步補齊七款；目前七款皆已有可操作原型，現階段重點轉為流程修正、跨電腦穩定性與現場驗收。

最終操作目標：工作人員開啟一個桌面程式，第一螢幕出現後台、第二螢幕顯示遊戲場域；玩家操作經 touch service 轉為遊戲輸入，同一個核心負責計時、判題、排名與存檔。

### Windows EXE 啟動與交付

使用者確認遊戲最終需要以 Windows EXE 啟動。現有 Electron 打包流程已產生兩種候選交付形式：可攜式資料夾內的 `704-Brain-Game.exe`，以及 Squirrel 安裝程式 `704 腦力競賽-0.1.0 Setup.exe`。可攜式版本需連同整個 `704 腦力競賽-win32-x64` 資料夾交付，因為主程式依賴同層 Electron runtime 檔案及 `resources/`（內含 app.asar 與自包含 TouchService）；不可只抽出主程式 EXE。候選版另有 ZIP，解壓後可直接執行同一主程式。新實例會把自己的 EXE 路徑交給舊實例；舊實例透過正常退出流程關閉遊戲伺服器與其啟動的 TouchService，清理完成後才由 Electron 啟動新實例。首次從不支援交接的舊版升級時，需手動正常關閉一次舊版。現階段產物供驗收，不等同已完成正式現場驗收的發行版。

本次已逐頁閱讀原始 PDF 共 9 頁，並檢視場域圖、流程圖及遊戲表格。指定資料夾原先沒有程式或既有素材。本報告區分「使用者已確認」「企劃既載內容」「實作建議／待確認」，文件中的討論文字不視為額外執行指令。使用者後續回覆優先於原 PDF 與先前提案；未回覆事項不視為同意。

### 玩家人數版型與全場共用選單

玩家名單的當前人數決定使用企劃書第 2 頁哪個版型；1–3 人暫用 4 人版，4–8 人分別載入對應版面。4 人版在每位玩家所在牆面並列一個題目區與一個答題區，觸控只綁定答題區，地板顯示玩家進度與排名。5–8 人版將題目顯示在地板，答題區依 180°映射後配置：5 人為對面長牆 2、左右各 1、入口側可用牆面 1；6 人為對面 2、左右各 2；7 人為對面 2、左右各 2、入口側 1；8 人為對面 3、左右各 2、入口側 1。入口保留區在所有版型均不顯示可互動控制，也不會映射 TouchService 輸入。

大廳固定使用八個符合企劃場域位置的牆面選項區，與隨參賽人數變動的答題版型分開。七款啟用遊戲與隨機抽選各占一個牆面選項區，玩家共同操作同一份選單；不同選項同批被選取時拒絕該批操作。遊戲介紹確認／取消只出現在所選遊戲牆面，深色遮罩覆蓋原選項底圖，兩個圓形按鈕分別位於局部畫布 x=0.25／0.75、y=0.60，半徑為 0.125；TouchService 命中採同一圓形範圍。教學完成按鈕仍只顯示一組於地板中央，任一玩家長踩約 1 秒並於按鈕內放開，即開始 3 秒倒數。地板長踩範圍與 TouchService 正規化命中範圍對齊，入口保留區不映射輸入。

踩地雷、數字方格、數字速記等數字格盤將原 1 px 間距改為 3 px；地板 3 px 格線提升為 9 px，數字鍵外框由 1 px 加至 3 px。觸控命中區域維持原幾何。數字速記的每次錯按以 520 ms 紅色半透明遮罩閃現於個人答題盤，重複錯按會重新播放。所有投影進度與結算計分板的玩家／名次／狀態／分數文字統一放大 3 倍。

加入後，玩家按先後取得 P1、P2…編號。人數改變時程式更新版型與 CAVE／觸控映射，舞台與工作人員後台同步顯示玩家編號和位置；玩家依牆面相同編號移動，既有分數與參賽資料保留。版型由 `config/player-layouts.704.json` 描述，啟動時會逐一驗證 4–8 人的顯示面、輸入面、方向、重疊及入口安全距離。1–3 人沿用 4 人版是目前實作預設，用於支持使用者已確認不設 4 人最低開局限制。

計分採 PDF 表格與使用者第 8、9 項確認的規則：參賽人數 N、名次 r，積分為 N−r。例如 8 人為 7、6、5、4、3、2、1、0；4 人為 3、2、1、0。N 取本輪已加入的參賽區數量，在輪次開始時固定，不必由工作人員輸入；後續加入不能追溯改動既有成績。未加入任何區域時沒有可開始的小遊戲，這是流程必要條件，不另設最低 4 人限制。

並列例：8 人賽兩人並列第 2，分享第 2、3 名積分，兩人各得 5.5 分，下一名為第 4。一般未完成者仍為 0 分。踩地雷的未完成者以有效揭露安全格數排序，排在完成人員之後；進度相同則並列。數字速記依序列進度處理，詳見第 5 節。記憶撲克超時未完成選牌者直接取最低積分 0 分，多人未完成都為 0 分，不套用並列分攤而獲得較高積分。

## 4. 完整流程

| 狀態 | 玩家看到的畫面 | 進入下一步的條件 |
| --- | --- | --- |
| 啟動檢查 | 場域待機畫面 | 確認顯示器、場域設定、輸入服務；正式模式檢查通過 |
| 場次開始 | 待機／歡迎畫面 | 工作人員從後台按開始，進大廳並開始 45 分鐘計時；不要求先登記人數或分配位置 |
| 大廳 | 八個固定牆面區上的全場共用選單；地板顯示共同狀態 | 工作人員從後台加入玩家；全場共同使用一份選單選擇或隨機抽取遊戲。只有大廳接受加入 |
| 遊戲介紹 | 地板顯示目標與提示；所選遊戲牆面暗化底圖並顯示圓形確認／取消按鈕 | 玩家觸碰所選牆面的圓形按鈕確認後進入教學；取消返回大廳。隨機抽選也須先確認 |
| 教學 | 周圍牆面顯示教學；地板只有一個全場共用完成按鈕 | 閱讀時間不限；任一玩家在地板長踩約 1 秒，或工作人員代為完成後開始 3 秒倒數 |
| 倒數 | 玩家區域高亮、3／2／1 | 鎖定名單、題目與規則；倒數結束接受作答 |
| 競賽 | 題目、答題區、個人狀態、輪次計時 | 遊戲專屬完成條件、輪次到時，或工作人員中止 |
| 小結算 | 正解、當輪名次、加分、累積分數 | 原則展示 5 秒；若場次已到時，轉總結算 |
| 下一輪／回大廳 | 同款下一輪或遊戲選單 | 同款尚有輪次就開始下一題倒數；組結束回大廳，重選同款仍展示教學 |
| 總結算 | 總排名、分數、參與遊戲紀錄、合照版面 | 畫面保持；工作人員按「遊戲結束」才回待機 |

補充：隨機抽取只從已啟用的遊戲清單選取，並先展示抽選結果等待玩家確認。題目抽取盡量避開同場重複，題庫耗盡時應有明確政策。暫停時停止場次、輪次、鎖答與教學倒數，拒收作答；繼續時先顯示 3 秒準備倒數，避免恢復瞬間有人先按。投影端若 SSE 靜默或中斷，會以 HTTP 輪詢補取最新狀態；狀態新舊比較與事件序號檢查可避免舊回應蓋過新畫面。投影恢復更新不會解除保護性暫停，仍須由工作人員操作繼續。

同一瞬間輪次到時與作答的先後，以核心收到事件的單調時鐘為準；到該輪作答截止時間即停止接受新答案。場次 45 分鐘到時僅標記不再開新輪，正在進行的輪次仍可繼續作答到完成條件或該輪截止。每次結算只能入帳一次，重複封包、切換頁面或畫面重連不得重複加分。競速提前結束須至少有一位真正完成；單人測玩不因 N−1＝0 而立刻結束。

### 記憶撲克的階段時間（依使用者授權定義）

| 階段 | 時間 | 行為 |
| --- | --- | --- |
| 開輪倒數 | 3 秒 | 全員同步準備，不接受選牌 |
| 記憶 | 20 秒 | 顯示 16 張牌，玩家記住牌面與位置 |
| 選牌 | 10 秒 | 16 張牌蓋牌，公開 3 張公共牌；每位玩家選 2 張不同位置的牌，可與其他玩家選到相同位置 |
| 揭曉倒數 | 3 秒 | 選牌結束並鎖定，倒數後公開勝負，不再補選 |
| 結果與積分 | 5 秒 | 顯示各人的 5 張牌、牌型、名次與加分；此段就是本輪小結算，不重複加一段小結算時間 |

每輪固定 41 秒，5 輪約 3 分 25 秒，另加首次教學與大廳時間。沿用企劃的 20 秒記憶、10 秒選牌與 3 秒揭曉緩衝，補上共用的倒數與結算時間；不為了湊滿原稿的 90 秒而加入等待。場次到時仍完成正在進行的這一輪後總結算。

選牌操作的實作預設：10 秒內可調整選擇，按確認後鎖定；到時若已選滿 2 張則自動提交，未選滿 2 張視為未完成，直接得 0 分。未完成者不隨機補牌；多人未完成者皆為 0 分。完成選牌者依牌型排名，同牌型再依企劃比較點數與餘牌，不比較答題速度或花色。

每輪題目使用加密亂數產生的 32 位元種子，並記錄 RNG 演算法版號、題目生成器版號、規則版本及題目識別碼。題目與數字速記個人位置變體由同一個確定性亂數流生成；相同遊戲、輪次、種子、規則設定及參賽區順序會產生相同內容。種子與題目資料保存於輪次結果及 JSON／CSV 匯出，不傳給遊戲投影端。第一版以程式生成並用解答器驗證，搭配人工檢視題圖；不讓現場出題依賴即時 AI 回應。每款先準備至少一整組可玩的題量，首批驗收後再擴充難度與避免重複的題庫。

### 時長與題量需要特別修正

PDF 原始標示若七款各跑完整組，合計約 65–67 分鐘，還沒加上大廳、教學與結算。使用者第 10 項已確認：45 分鐘內自由選遊戲，不要求七款全玩。新規劃的記憶撲克時間以本節階段表為準，其餘遊戲亦應依實際完成條件計時；另提供開發用縮短模式。

競速遊戲的每輪時間是上限，不保證耗時等於「輪數×上限」；小結算與教學另占時間。記憶撲克按上述固定階段運行，不使用原稿互相不一致的「每輪約 90 秒／5 輪約 10–12 分鐘」估計。階段時間保存為設定，後續測玩可調整。

使用者第 9 項已確認沿用每輪累計方式，不做各遊戲積分權重正規化；20 輪遊戲的總分上限會高於 5 輪遊戲。

## 6. 場域與雙螢幕設計

第一螢幕為工作人員控制台，第二螢幕為完整遊戲輸出。第二螢幕內還可能包含左牆、右牆、正面牆、地板與東小牆等區塊；作業系統的第二螢幕不等於單一玩家區。

使用者第 14 項已指定沿用 TouchService 場域設定，並要求所有遊戲介面視角正確。TouchService 原生輸出畫布是 2688×3840；第二螢幕會自動選用主要螢幕以外的第一台顯示器並全螢幕投播。遊戲以固定 2688×3840 TouchService 場域畫布全螢幕投播至第二螢幕，並依可用視窗等比例置中縮放，螢幕比例不同時也不裁切場域；啟動器不更改 Windows 顯示模式。當顯示模式為 2688×3840 時為 1:1 輸出，其他模式會在後台提示操作員調整以取得 1:1 像素對應。服務畫布方向、CAD 檢視方向與玩家面向牆面的閱讀方向分開處理。

玩家局部介面依 TouchService 面向配置：玩家站在場內面向牆面時，介面文字上緣朝向該牆外側，文字、數字鍵盤、選項、教學、分數及第 9、10 排心數都須正向可讀；旋轉後觸控座標以同一角度反算，確保顯示與命中一致。服務畫布直接採 2688×3840；目前答題區與題目板仍在 CAD 展開幾何中配置，輸出時將 CAD 畫面整體逆時針旋轉 90°回到服務畫布。此後的各面閱讀方向對照 TouchService `reservedSide`：face 0 左牆 270°、face 1 下牆 180°、face 3 上牆 0°、face 4 入口側牆 90°，與踩地雷 HUD 方向相符。場域實體排號由下往上，第 9、10 排為高處資訊列，下方第 1–8 排才是作答區。遊戲棋盤 10×8 指玩家視角下 10 欄、8 列，程式陣列列號與實體排號分開，畫布旋轉後不可誤把上下換成左右。地板共用題目沿用場域方向並保持題意一致，不能只因旋轉讓部分玩家看到不同答案。

先前視角回報指出有玩家區顛倒及 P8 接近出口的疑慮。重新從 TouchService `venues/704.json` face origin／尺寸推導，再與 `VENUE_GRID_704.md` CAD 轉換比對：原生畫布 2688×3840 逆時針旋轉 90°並排除 512 px 空白後，形成 3328×2688 CAD 展開圖；遊戲輸出再逆轉回服務方向。企劃 8 人配置採使用者同意的 180°映射：對面長牆 3 區、兩側牆各 2 區、入口側可用牆面 1 區。入口保留區 CAD 座標是 (896,2048,512,640)。P8 改放至 (2048,2048,640,640)，位於入口右側牆面最外段，距入口保留區 640 px；玩家輸入來源仍是 face 4，入口 face 5 不配置玩家輸入。逆轉後玩家畫面方向依 face 為 0 左牆 270°、1 下牆 180°、3 上牆 0°、4 入口側牆 90°，與踩地雷程式的 left／bottom／top／right 旋轉表一致。入口區以單色粒子動畫標示並設為 `pointer-events:none`。自動測試逐區核對 CAD 到服務畫布的映射、方向及入口距離；現場投影與感應器仍須逐面校正，瀏覽器測試不能替代實地驗收。

## 7. touch service 串接規劃

已收到並唯讀檢閱服務目錄：`使用者提供的 NangangProjection-git/TouchService 專案目錄`。核對內容包含 `docs/PROTOCOL.md`、`docs/DEPLOY.md` 相關段落、`docs/VENUE_GRID_704.md`、`venues/704.json`、`config.json`、序列化與座標轉換原始碼。本次未修改、啟動或測試既有服務，以下為靜態閱讀結果，不代表現場設定或已發布 exe 必然與此份原始碼相同。

**建議直接使用既有 WebSocket JSON v1，預設端點為 `ws://127.0.0.1:20111/`。** 感應器的 UDP 20001 繼續由 TouchService 接收；遊戲訂閱整理後事件，無須另搶硬體接收埠。服務另有 UDP JSON 輸出 20110，但第一版只選一條輸入管道，避免同筆觸控重複送入。TUIO 在協定文件中仍是未實作的預留項，不列為本案依賴。

預定輸入路徑：

`感應器 UDP → TouchService 追蹤與校正 → WebSocket v1 → 遊戲區域映射 → 玩家操作事件 → 遊戲核心 → 畫面與成績`

開發模擬器走同一條核心輸入介面，讓滑鼠／鍵盤與真實觸控使用相同判題流程。滑鼠模擬不能當作已通過多人實機測試。

| 項目 | 預計作法 |
| --- | --- |
| 事件格式 | 實際 frame 有 `v`、`seq`、`t`、`venue`、`canvas`、`events`、`alive`；事件有 `id`、`phase`（down／move／up）、`face`、`cell`、`px`、`norm`。取消是遊戲端合成事件，並非原生 phase |
| 座標轉換 | 優先用已校正的 `face`＋`px` 做玩家區域與按鍵命中；保留完整服務畫布作邏輯座標，再套用遊戲輸出縮放／旋轉。raw 校正留給既有服務，不在遊戲重做一次 |
| 玩家歸屬 | 以觸點所在的玩家區域映射 playerId；接觸 ID 只是追蹤一次接觸，不能當作人的身分 |
| 多人同時輸入 | 各觸點獨立追蹤；同一玩家跨牆面、同時多指及同一鍵重複接觸都要訂規則 |
| 點擊與長按 | 建議普通作答在有效 down 時提交一次，保持接觸不能連續作答；長按另外追蹤。服務目前 release timeout 為 170ms，不把延遲 up 當玩家答題完成時間 |
| 防誤觸 | 已完成、暫停、鎖答、倒數及非作答區不接受答案；連續事件不重複提交 |
| 斷線 | 每包用 `alive` 全清單清理失蹤 ID；目前 keepalive 為 1000ms。逾時門檻建議先設 3 秒並可調，逾時暫停；重連後清空舊接觸與 seq 基準，重新驗證 hello，再由工作人員恢復 |
| 診斷 | 顯示連線、觸點、區域命中、事件頻率及延遲資料；可錄製輸入並回放重現問題 |

上表由 profile 與 `SensorFaceConfig.cs` 的 cell 尺寸推得。CAD 預覽可旋轉 90 度，但這只是檢視轉換，不能直接改寫觸控座標。正式運作以 hello／`GET /venue` 提供的場域為準；設定與預期 704 配置不符時停止開局並提示。rawMax 邊緣可能輸出到面外邊界，命中測試須依 face 做邊界夾限／排除，不能把邊緣觸點誤派到相鄰玩家。

### 訊息解析與啟動狀態

1. 連線先讀 `type:"hello"`，驗證版本、venue、canvas 與 faces；一般觸控 frame 沒有 type。帶 type 的 locks／log／raw／calibration 分開處理，未知 type 忽略。
2. `hello`／`locks` 的 `autoLockActive` 為 true 時，自檢尚未完成，觸控不會正常發布。現有設定自檢窗 10 秒；遊戲端已保持輸入未就緒並顯示剩餘自檢時間，直到收到 `locks` 的 `autoLockActive:false` 才開放操作，不能固定睡 10 秒就假設成功。
3. 服務有 `interactionEnabled` 總開關。false 會停用互動輸出，與「連線失敗」不同；後台應區分已連線／自檢／互動停用／可互動。此狀態位於管理 API，需以已部署版本適配；僅 WebSocket 連上不能證明觸控可用。
4. 目前設定 `maxSlots:128`、`matchRadiusPx:96` 是追蹤容量與合併半徑，不是已證明能辨識 128 位玩家。相鄰按鍵、多指與同一隻手觸發多晶片必須現場驗證，遊戲端再做語意防重複。
5. 建議維持 `touchMode:grid`，讓遊戲只接 WebSocket。mouse 模式會額外注入 OS 游標，即使 WS 仍有事件，也可能誤按工作人員後台或造成雙重輸入；正式部署檢查模式，不在遊戲局中偷偷切換。

### 一鍵啟動與既有服務的分工

啟動器先確認是否已有相容服務；有就連線，沒有才依設定的 exe 與 `--config` 啟動。不得僅看到埠占用就視為正確服務，也不能為了遊戲重複啟動感應器接收程序。已有服務由外部管理時，關閉遊戲只斷開訂閱；由啟動器建立的服務才納入啟動器自己的程序生命週期。

現有 `config.json` 設為 `ui.autoLaunch:true`，會開啟服務監控頁。正式遊戲包建議使用專案自己的部署設定，設 `ui.autoLaunch:false`，由遊戲後台提供「開啟觸控診斷」入口；營運後台與服務診斷分工處理。這是後續部署方案，本次未改動原服務設定。

桌面包隨附 `runtime/touch-service/` 的自包含 win-x64 單檔執行版本、704 profile 與來源雜湊資料；Electron package 將服務放在 `resources/touch-service/`，不放進 `app.asar`。`scripts/build-touch-service-runtime.ps1` 先確認服務來源中的程式、設定與 profile 沒有未提交修改，再複製到本專案 `tmp/` 建置；建置後以隔離 UDP／WebSocket 埠實際啟動並驗證 704 hello，再更新 runtime 目錄。原 TouchService 工作目錄保持唯讀。啟動器先尋找隨包／專案內 runtime，再回退至設定的 `serviceRoot`；`TOUCH_SERVICE_ROOT` 保留人工覆寫入口。

實作驗收仍須核對服務發布版本、讀取實際螢幕尺寸、依 TouchService 配置驗證輸出方向，以及測試有效觸點與相鄰操作分辨能力；這些是技術驗證，不再列為未取得使用者決策。遊戲介紹控制由所選遊戲牆面輸入；地板輸入只用於教學長踩，競賽題目顯示面不接受答題輸入。答題區幾何校驗不等於營運時管理玩家站位。第一階段可先寫 v1 訊息模擬與轉接器，不必等正式後台完成。

## 8. 共用核心與後台範圍

共用核心保存場次、參賽名單、遊戲組、輪次、題目、計時、答案、懲罰與成績，兩個視窗讀取同一狀態來源。控制台送出「開始／暫停／結束」命令，玩家畫面送出「選擇／輸入／確認」命令，不能各自算分或各自倒數後互相覆寫。

建議最小資料紀錄：sessionId、playerId、位置、加入／離場時間、roundId、gameId、題目版本與種子、規則快照、參賽人數、有效操作、完成時間、懲罰、名次與加分。每輪先落盤再播結算，異常重開時可辨識未完成輪次；首版恢復到最近完成的輪次，未完成輪次作廢重開，不宣稱能無損續玩到任意毫秒。

第二階段後台包含：

- 場次控制：45 分鐘場次開始、暫停、繼續、提前結算、結束與重置；工作人員可隨時介入。
- 參賽狀態：查看已加入答題區、顏色／代號與個人成績；玩家只能由工作人員在大廳透過後台加入，不另設必填人數、位置分配或離場審核流程。
- 遊戲設定與介入：啟用清單、難度、輪數、時限與懲罰設定；日常選遊戲與開始由玩家操作，後台保留手動介入入口。第一版不提供限時解題提示或其設定。
- 狀態監看：當前遊戲、剩餘時間、玩家完成狀態、分數、touch service 與輸出狀態。
- 顯示設定：控制台／遊戲螢幕指定、4–8 人場域配置、解析度、方向、校正模式。
- 紀錄與維護：場次結果匯出、錯誤／輸入日誌、題庫載入檢查與備份設定。

目前這個開發原型以開始、暫停、重置與回大廳介入入口驗證遊戲；輪次依遊戲流程自動接續，不提前視為完整營運後台。

目前工作人員控制台已有場次開始／暫停／繼續／結束、教學介入、重開／作廢輪次、選擇遊戲、參賽區與成績檢視。遊戲設定區新增啟用遊戲的逐輪題目預檢：使用目前尚未儲存的設定草稿，逐輪生成題目並核對答案不變條件；只顯示通過輪數與失敗原因，不回傳題目、答案或種子，場次進行中不可執行。Electron 啟動器已改為首次啟動自動將控制台放主要螢幕、遊戲投播放第一台非主要螢幕，並全螢幕使用 TouchService 2688×3840 畫布；螢幕設定仍可人工辨認及覆寫。螢幕像素尺寸不是 2688×3840 時，後台提示在 Windows 顯示設定中調整。TouchService 啟動管理會先驗證 hello，必要時以使用者資料目錄中的設定副本啟動服務；開發機實際 hello 已通過 704 場域幾何驗證。歷史場次支援 CSV／JSON 匯出，營運事件與輸入寫入 JSONL。
